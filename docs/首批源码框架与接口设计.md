## 2. 模块职责边界

| 模块 | 负责什么 | 不应承担什么 |
|---|---|---|
| Core | 数据模型、接口、能力描述、操作结果 | 访问硬件、绘制界面 |
| Application | 协调控制顺序、共享状态、启动和供电策略 | 存放寄存器地址 |
| Monitoring | 定时采样、来源选择、有效期判断 | 修改功耗和风扇 |
| Fans | 曲线校验、配置应用、校准、强冷与恢复 | 直接操作窗口 |
| Performance | 五档配置、CPU/GPU 限制、睿频上限 | 自己定时争抢硬件设置 |
| Graphics | 显卡模式能力、切换条件、待生效状态 | 自动重启 |
| Hardware.Msi | WMI/ACPI 等实际访问、设备识别与适配 | 决定用户界面行为 |
| Persistence | 配置读写、版本迁移、备份、有限日志 | 应用硬件设置 |
| Desktop | 两种窗口、曲线编辑器、主题、托盘、快捷键 | 绕过协调层直接写硬件 |

## 3. 共享模型

先写共享模型，避免各模块各自解释同一个数值。第一批模型重点解决“请求值”和“实际状态”的区别。

```csharp
public enum ReadingStatus
{
    Valid,
    Sleeping,
    Unavailable,
    Stale
}

public sealed record SensorReading(
    double? Value,
    string Unit,
    ReadingStatus Status,
    string Source,
    DateTimeOffset? SampledAt);

public enum OperationStatus
{
    Succeeded,
    PartiallySucceeded,
    Failed,
    PendingRestart,
    Unsupported
}

public sealed record SettingResult(
    string Setting,
    string? Requested,
    string? ReadBack,
    OperationStatus Status,
    string? Message);

public sealed record ControlResult(
    OperationStatus Status,
    IReadOnlyList<SettingResult> Settings);
```

`Succeeded` 必须有明确的确认依据；不能只因为调用没有抛异常就显示成功。无法读回的操作要注明确认方式和限制。

性能配置用明确类型表达“原生上限”，不要拿 0 或极大数字代表无限：

```csharp
public enum LimitMode
{
    Native,
    Custom
}

public sealed record PowerLimit(
    LimitMode Mode,
    decimal? Watts);

public sealed record CpuTurboLimit(
    LimitMode Mode,
    int? Megahertz);
```

每档模式拥有独立功耗、睿频和双风扇配置。CPU 的持续与短时限制分别保存；GPU 替代节能策略也单独记录，避免把替代策略误显示成精确瓦数限制。

## 4. 硬件接口

硬件接口先定义成小接口。

```csharp
public interface IMonitoringProvider
{
    Task<MonitoringSnapshot> ReadAsync(
        CancellationToken cancellationToken);
}

public interface IFanHardware
{
    Task<FanHardwareState> ReadAsync(
        CancellationToken cancellationToken);

    Task<ControlResult> ApplyCurveAsync(
        FanChannel channel,
        FanCurve curve,
        CancellationToken cancellationToken);

    Task<ControlResult> SetAutomaticAsync(
        CancellationToken cancellationToken);

    Task<ControlResult> SetFullSpeedAsync(
        bool enabled,
        CancellationToken cancellationToken);
}

public interface IPerformanceHardware
{
    Task<PerformanceHardwareState> ReadAsync(
        CancellationToken cancellationToken);

    Task<ControlResult> ApplyAsync(
        PerformanceSettings settings,
        CancellationToken cancellationToken);
}

public interface IGraphicsHardware
{
    Task<GraphicsHardwareState> ReadAsync(
        CancellationToken cancellationToken);

    Task<ControlResult> RequestModeAsync(
        GraphicsMode mode,
        CancellationToken cancellationToken);
}
```

曲线校准和模式切换流程放在业务模块，底层接口只负责真实访问。所有接口都带取消和超时机制；写入开始后，取消请求不能让程序跳过必要的状态核对。

## 5. 控制协调器

正常窗口、迷你窗口、托盘、快捷键和供电事件都向 `ControlCoordinator` 发请求。

```text
用户操作 / 供电变化 / 启动恢复
                 ↓
        ControlCoordinator
                 ↓
检查能力与条件 → 顺序应用设置 → 读取确认
                 ↓
       更新共享状态和操作结果
                 ↓
        正常窗口 / 迷你窗口
```

协调器需要做到：

- 硬件写入串行执行，避免性能切换和风扇编辑互相覆盖。
- 合并尚未执行的过期请求，尊重最新手动选择。
- 每个设置单独报告结果。
- 出现部分失败时读取当前状态，不盲目宣称整组回滚成功。
- 恢复启动设置前检查设备、配置和当前供电状态。
- 重新插电时，依据拔电后是否发生手动选择决定是否恢复原模式。

监控则使用一个共享采样任务。窗口只订阅结果，不各自创建计时器读取硬件。

## 6. 硬件适配层的证据边界

`Hardware.Msi` 建议再分为：

```text
Hardware.Msi/
├─ Discovery/       型号、固件、接口枚举
├─ Transport/       WMI/ACPI 等访问封装
├─ Devices/
│  └─ Ms15M3/       本机已验证的方法和数据格式
└─ Capabilities/    各项功能的支持与验证状态
```

接口参数和寄存器含义必须来自源码、接口定义或实机证据。第一轮源码中，不填猜测的 EC 地址，也不把尚未确认的能力默认设为支持。

未完成真实硬件适配时，界面显示“尚未适配”。开发用模拟数据只能通过显式开发选项启用，并始终标注“模拟”，不能进入默认运行流程。

## 7. 首个可运行版本的范围

- 正常窗口与迷你窗口切换。
- 五档性能按钮、三种显卡模式入口。
- CPU/GPU 八项读数与整机功耗位置。
- 风扇编辑器入口。
- 跟随系统主题。
- 托盘、单实例和退出逻辑。
- 本地配置读写。
- 未适配能力的禁用说明。

仪表和曲线优先使用 WinForms 自绘控件，减少大型 UI 依赖。先验证 DPI、鼠标拖动和刷新开销，再决定是否引入图表库。

## 8. 实施顺序

| 顺序 | 首先完成的内容 | 完成标准 |
|---|---|---|
| 1 | Core、配置模型与接口 | 各模块对单位、状态和结果有一致定义 |
| 2 | 桌面壳、配置、共享状态 | 两种窗口能运行，配置可保存 |
| 3 | 统一监控 | 真实读数、休眠和失败状态正确 |
| 4 | MSI 风扇适配与编辑器 | 读取、应用、强冷和恢复逐项验证 |
| 5 | 性能与功耗 | 五档配置可编辑，逐项确认结果 |
| 6 | 显卡切换 | 能力、外接屏条件和待生效状态正确 |
| 7 | 自动策略与资源优化 | 启动、供电、唤醒及占用符合设计 |

## 9. 需针对性测试的核心

- 曲线和配置校验。
- 供电状态转换。
- 请求优先级。
- 部分失败处理。
- 配置迁移。

硬件是否真实生效仍须实机验证，模拟测试不能替代。

## 10. 首批实际落盘目标

先交付：可编译的工程骨架、正常/迷你窗口、共享模型、配置存储和控制协调器。

随后优先接入真实监控与风扇，功耗和显卡控制保持清晰的独立模块。这样既能尽早看到程序，也能把最重要的风扇能力集中做好。
