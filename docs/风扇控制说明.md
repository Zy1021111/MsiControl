## 2. 实机关键发现（详见 evidence §13）

1. **`Data` 参数的运行期形态是内嵌 CIM 实例 `root\WMI:Package`**（单一属性 `Bytes`，
   `UInt8[]`）。这是此前所有 `0x80041005` 类型不匹配的根因：`System.Management` 无法把
   .NET 标量/数组映射成 CIM `Object`（VARIANT），必须传入 `Package` 实例。
2. **`Get_Fan` 的输入必须恰好 16 字节**；`Bytes` 全 0 的 16 字节请求可复现地返回 32 字节。
3. 32 字节缓冲区的**字段语义未确证**：代码层 `TryDecodeFanReport` 恒拒绝解码，
   绝不由猜测冒充读数（任务书 §1 原则 5/6）。
4. 写入有两道独立闸门：能力等级未达 `Verified` + 写入载荷编码无证据
   （`FanAcpiPayload.CanComposeWriteRequest` 恒 `false`）。

## 4. 关键设计决策

1. **`MsiControl.Fans` 引用 `MsiControl.Hardware.Msi`（而非只引用 Core）。**
   理由：曲线二次校验需要硬件报告的 `FanCurveLimits`（设备事实），且读回核对需要
   原始诊断通道（`IFanRawDiagnostics`）。这是向下依赖，无环；与任务 03 的
   `MsiControl.Monitoring` 消费 `Hardware.Msi` 的模式一致。
   - 代价：`MsiControl.Fans` 与 `MsiControl.Fans.Tests` 的目标框架是 `net8.0-windows`。
   - **建议（转 01/07）**：待整合时把 `FanCurveLimits` 这类「设备无关的硬件约束类型」
     上收到 `MsiControl.Core`，即可去掉该依赖、恢复 `net8.0`。
2. **「未知 ≠ 允许」。** `FanCurveLimits` 用 `null` 表达未取得证据的约束，
   `UnverifiedConstraints` 逐个列出；`FanCurveValidator` 因此**拒绝写入**任何受未验证
   约束影响的曲线，而不是静默放行。
3. **四态严格区分**（任务书 §7.4）：编辑中 / 本地保存 / 最近成功应用 / 当前硬件状态
   由 `FanConfigurationState` 统一承载，`Describe()` 固定四行，供界面逐行展示。
4. **首次写入前快照**（`FanBootSnapshotStore`）只在进程内保存、只捕获「可信」的读取结果、
   已捕获后不覆盖；「恢复启动曲线」明确标注**不是 BIOS 出厂重置**。
5. **成功必须有确认依据。** 业务层「成功」只由读回值与请求一致判定
   （`FanCurveComparison.AreEquivalent`），确认依据写入 `FanOperationResult.ConfirmationBasis`；
   `FanOperationResult.Validate()` 在测试中检出「无依据的成功」。
6. **取消不跳过核对。** 写入后即使被取消，仍完成读回（带时间上限）并记录到
   `LastReadBack`，再把取消异常原样抛出（任务书 §16）。

## 5. 接入方式（给任务 07）

```csharp
using MsiControl.Hardware.Msi.Capabilities;
using MsiControl.Hardware.Msi.Devices;
using MsiControl.Hardware.Msi.Transport;

var device = /* Discovery 得到的 DeviceIdentity */;
var capabilities = CapabilityBaseline.ForDevice(device);

var hardware = new FanHardwareMs15M3(
    new WmiMsiAcpiTransport(),          // 只读通道
    capabilities);

var application = new FanApplicationService(
    hardware,
    FanCurveLimits.Ms15M3,              // 硬件报告的约束
    capabilities);

var calibration = new FanCalibrationService(application, capabilities);
```

要点：

- 全部入口的启用状态取自 `capabilities`，文案用 `FanCapabilitySummary.Describe(...)`；
  **不可用入口必须给出原因**（任务书 §1 原则 8）。
- 写入走 `FanApplicationService`，**不要**直接调用 `FanHardwareMs15M3` 的写方法：
  业务层负责前置判断并返回 `FanOperationResult`，适配层只做最后一道防御。
- 曲线 UI 由任务 02 的编辑器承载，本模块只提供数据与执行（提示词 §四.11）。
- 五档曲线的容器用 `FanStageCurveSet`（本模块）；存储归 02，档位编排归 05/07。

## 6. 待 01 / 07 处理的事项（接口观察，不属本任务可自行解决）

1. **`ControlResult.From` 的归并规则**：当所有项都是 `Unsupported` 时，整体状态为
   `PartiallySucceeded`（规则「无失败但存在不支持 → 部分成功」）。
   这对「整组都不支持」的结果并不贴切（会显示「部分成功」）。建议 01 追加一条规则：
   「全部为 `Unsupported` → `Unsupported`」。
   - 业务层（`FanApplicationService`）不依赖该整体状态：被拦下时直接返回
     `FanOperationResult`（`Unsupported`）且**不产生** `ControlResult`，因此该问题目前
     只影响直接调用适配层时的展示，不影响风扇模块的正确性。
2. **`IFanHardware` 缺少「按周期下发输出百分比」的方法。**
   软件调速策略（`SoftwareFanPolicy` / `SoftwareFanControlLoop`）已实现滞回、升降速节流、
   传感器超时、睡眠唤醒与异常退出说明，但当前契约无法把决策下发到硬件。
   若日后实测必须软件持续调速（任务书 §7.6），需 01 扩展契约后闭环。
3. **`FanCurveLimits` 等设备无关约束类型建议上收 `MsiControl.Core`**（见 §4.1）。

- 「自定义曲线编辑需要 EC 手动占空比写寄存器证据」的旧结论作废：证据已取得。

### 10.2 软件曲线引擎（FanCurveEngine，MsiControl.Fans）

- 周期：默认 1 秒（HWE §23 实测固件 ≤2 秒回写自身曲线值，1 秒周期可保持占空比生效）。
- 每周期：读温度（EC 温度寄存器）→ 曲线线性插值 → 升降速限幅（升 +20%/周期、降 -10%/周期）
  → `IFanOutputControl.SetDutyPercentAsync` 写 0x71/0x89 并读回核对。
- 安全边界：温度连续 5 次读取失败或写入连续 5 次失败 → 自动停机并交还固件
  （`AutoStopReason` 说明原因）；停止后不主动恢复任何曲线（固件数秒内自愈）。
- 生命周期：引擎独立于曲线窗口——应用曲线后关闭窗口，引擎继续运行；程序完全退出后停止。

### 10.3 曲线窗口（FanCurveForm，MsiControl.Desktop）

对应图示页面：控制模式分段（自动/手动）、CPU/GPU 曲线双标签页、配置档工具栏
（下拉/重命名/导出/恢复启动曲线/保存/导入/应用）、「有未应用修改」徽标、
排序（最近修改/名称）+ 配置标签过滤 + 保存标签、七列垂直滑块编辑器
（节点温度可编辑、占空比 0–100）、状态行。

- 配置档持久化：`fan-curves.json`（`FanCurveProfileStore`，原子写、损坏隔离），
  含排序/标签过滤/选中项偏好。
- 「手动/应用曲线」= EC 0xD4→0x8D（经协调器）+ 引擎启动；
  「自动/恢复启动曲线」= 停引擎 + EC 0xD4→0x0D。
- 接缝：`ShellContext.FanCurve`（FanCurveServices）携带引擎与配置档存储；
  窗口不接触 IFanHardware（任务书 §16 规则 11 保持）。

### 10.4 语义边界（必须向用户展示）

- 软件持续调速依赖本程序存活：两次写入之间固件可能短暂接管（回写竞争），
  表现为占空比在目标值附近的小幅波动，属预期而非故障。
- 程序退出（含崩溃）后固件在数秒内用自身曲线接管，无残留风险。
- 「恢复启动曲线」= 停引擎 + 切回固件自动策略（0xD4=0x0D），不是 BIOS 出厂重置。
- 整条曲线固件写入（ApplyCurveAsync）维持不支持：固件无曲线表寄存器。

## 11. 风扇「转一下停一下」的成因与修复（2026-10-31）

### 11.1 现象与证据

实机日志（13:06–13:07，平衡档位、曲线 `温度[0,50,55,60,75,81,87] → 占空比[0,0,0,0,40,45,50]`）：

- 引擎每秒下发 `CPU 0% @ 59–63°C`，间或 `3% / 5% / 8%`；
- GPU 通道出现 `Gpu 占空比下发失败：写入后读回 24%，与请求 0% 不一致`。

即：**0% 不是固件能保持的状态**。写 0 后立即读回的是固件自身曲线值（24%），
于是寄存器在「我们写的 0」与「固件写的 24%」之间以 1–2 秒周期来回，
风扇被驱动物理表现为**转一下停一下**。再叠加曲线在 60°C 两侧由 0% 陡升，
温度 ±1°C 抖动就让目标在 0%↔8% 之间跳变，形成第二个极限环。

### 11.2 修复（`FanCurveEngine`）

| 规则 | 取值 | 作用 |
| --- | --- | --- |
| 曲线目标 0% → **交还固件** | — | 不再写 0，停止对该通道下发，由固件自身低转速曲线稳定维持；寄存器不再被拉成 0/24 交替 |
| 可维持下限 | `MinimumControlledDuty = 20%` | 目标 1–19% 时按 20% 下发（此区间风扇只点动不成转）；首次抬升记一条日志 |
| 下行迟滞 | `TemperatureHysteresisC = 2°C` | 升温立即跟随，降温需真实温度低出 2°C 才下移，抑制节点边界抖动 |
| 重新接管 | 目标重新为正 | 交还后只有曲线目标回到正数才接管（接管即 ≥20%，不会停在启停临界） |

要点：**引擎任何时刻都不写 0%**。这条不变量同时消除了「0% 读回不一致」告警。

### 11.3 界面语义

- 曲线区标题明示「0% = 交还固件调速」；
- 状态行对交还通道显示 `CPU/GPU 已交还固件（曲线目标 0%）`，不再显示成 0% 生效；
- 想真正安静请把低温度段设为 20%（可维持转速）；设 0% 等于让固件按它的曲线跑，
  这在本机是唯一能稳住不抖的做法。

### 11.4 未解决／边界

- 固件在 advanced 模式下仍会周期性回写自身曲线，接管期间占空比会在目标值附近小幅波动
  （属预期，非启停）；
- 「风扇完全停转」在本机**无可用写入通道**（固件不接受 0%），因此软件无法提供零转速模式。
