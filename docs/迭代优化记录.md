## 1. 第 1 轮 · 健壮性：构造期不变量

### 发现的问题

1. **`SensorReading` 是公开位置构造**，可造出矛盾对象：
   - `Status = Valid` 但 `Value = null` → 调用方若按 `Status == Valid` 分支后直接访问
     `Value.Value` 会抛 `NullReferenceException`；
   - `Status = Unavailable` 但 `Value = 42` → 界面可能把陈旧值当当前读数显示。
2. **`CapabilityStatus` 同样是公开位置构造**，可造出 `Verified` 却无任何证据的对象。
   这与项目「不显示虚假成功」原则**直接冲突**，也与 `PowerLimit` 已有的私有构造设计不一致。
3. **`FanReading` 无范围校验**：负 RPM、超过 100% 的百分比均可构造。

### 依据

`PowerLimit` / `CpuTurboLimit` 已用私有构造 + 工厂把非法值挡在编译期之后
（任务书 §8.1「禁止用 0、-1 或极大数字表达无限」）。同样的手法应覆盖所有
「不变量必须成立」的契约类型，否则约束强度不一致。

### 改动

| 类型 | 改动 |
|---|---|
| `SensorReading` | 构造函数私有；`Valid` 必须有值且有采样时刻；`Sleeping`/`Unavailable` 禁止携带数值；`Stale` 允许保留诊断值 |
| `CapabilityStatus` | 构造函数私有；`Verified`/`Detected` 强制证据；`Unsupported` 强制原因；能力键非空 |
| `FanReading` | 构造函数私有；RPM 不得为负；`ActualPercent`/`TargetPercent` 必须落在 0–100 |
| `DeviceCapabilities` | 新增 `MissingKeys()`，供启动自检发现基线与 `CapabilityKeys` 脱节 |

### 实测效果与意外收获

新增 31 项测试。首次运行 **1 项失败**，暴露的是**我的测试写错了**：
`CapabilityStatus.Unknown(" ")` 在构造期就抛异常，因此
`DeviceCapabilities` 内部那段空键校验**永远不可达**——已成死代码。

这是本轮复查的真正收益：直接构造的可行性消失后，下游的防御性重复校验失去了意义，
留着会误导读者以为上游仍可能给出空键。已删除该分支，测试改为断言真正的保证链。

## 2. 第 2 轮 · 准确性：状态标记完整性与新鲜度

### 发现的问题

1. **`MarkStale` 覆盖不全**：只改写 CPU/GPU 的温度、频率、功耗，
   **遗漏双风扇、整机功耗与扩展传感器**。采样超时后这些读数仍为 `Valid`，
   界面会继续显示陈旧值——这正是任务书 §6.4「过期数据明确标注」要防的情形。
2. **更严重：`MarkStale` 会改写本来就不是 `Valid` 的读数。**
   原实现无条件调用 `AsStale`，于是：
   - `Unavailable`（读不到）→ 被改写成 `Stale`（数据旧了）
   - `Sleeping`（独显休眠，正常状态）→ 被改写成 `Stale`

   这**抹平了三种本质不同的状态**，把故障和正常休眠伪装成「数据过期」。
3. 缺少「是否过期」的判定能力，只能靠外部布标记。

### 依据

任务书 §6.4 明确要求四种状态分别表达：有效 / 休眠 / 不可用 / 过期。
把它们互相改写，等于让界面无法区分「设备休眠」与「接口坏了」。

### 改动

- 新增 `SensorReading.AsStaleIfValid`：**仅当原本有效时才转过期**，否则原样返回；
- `MarkStale` 覆盖全部读数组（含风扇、整机功耗、扩展传感器），且保留功耗口径字段；
- 新增 `MonitoringSnapshot.IsFreshAt(now, maxAge)` 与 `SensorReading.Age(now)`。

### 实测效果

新增 11 项测试，其中 3 项专门锁死回归：`
MarkStale_DoesNotRewriteUnavailableAsStale`、
`MarkStale_DoesNotRewriteSleepingAsStale`、`MarkStale_IsIdempotent`。

## 3. 第 3 轮 · 正确性：判定逻辑缺陷

### 发现的问题

1. **`IsSameBoardAs` 会把两台未识别的设备判为同机型。**
   `DeviceIdentity.Unknown` 的主板码是 `"Unknown"`，另一台没读出主板码的设备若也用
   `"Unknown"`，字符串相等 → **返回 `true`**。
   后果：**跨机型的配置导入被错误放行**，直接违反任务书 §2.2
   「按功能判断能力，不把同品牌或同系列视为全功能支持」。
2. **`PerformanceSettings` 的字段组合无人校验**（`PowerLimit` 只保证单值合法）：
   - 可构造「短时上限 10 W、持续上限 60 W」这种自相矛盾配置，
     使「CPU 默认严格限制持续与短时」的要求无法成立（§8.2）；
   - 可把 CPU 曲线绑到 `FanChannel.Gpu`，反之亦然——实践上会把曲线写到错误的风扇上。

### 依据

「配置校验」是任务书 §19 列出的自动测试重点之一，但基线里对**组合关系**没有任何校验点。

### 改动

- `DeviceIdentity`：新增 `IsIdentified`（主板码非空且不等于占位值）；
  `IsSameBoardAs` 改为**双向要求已标识**；新增 `UnknownBoardCode` 常量。
- `PerformanceSettings`：新增 `Validate()`，检查短时 ≥ 持续、曲线通道归属。

### 实测效果

新增 9 项测试。附带收益：`PerformanceProfileCatalog` 五档默认表在新增校验下
**全部通过**，说明既有默认值自洽。

## 4. 第 4 轮 · 封装与跨区域性

### 发现的问题

1. **`FanCurve.Points` 的不可变性可被绕过。** 属性类型是 `IReadOnlyList<FanPoint>`，
   但底层是 `FanPoint[]`，调用方一句 `(FanPoint[])curve.Points` 即可就地改写节点，
   使 `Interpolate` 与 `NodeCount` 的前提失效。
2. **`PowerLimit.ToString()` 依赖当前区域性。** `$"{Watts:0.##} W"` 在德语等区域
   会输出 `60,5 W`。本工程启用了 `InvariantGlobalization`，但
   **该设置作用于宿主进程而非库本身**——最终由 Desktop 承载时若未启用，
   界面数值格式会与预期不一致。

### 依据

契约层被 02–07 共同消费，不可变性与输出格式属于**对外承诺**，不能依赖调用方的环境配置。

### 改动

- `FanCurve`：节点改用 `Array.AsReadOnly` 只读包装视图，字段声明为 `IReadOnlyList<FanPoint>`；
- `PowerLimit` / `CpuTurboLimit` 的 `ToString` 显式使用 `CultureInfo.InvariantCulture`。

### 实测效果

新增 6 项测试，含 `Points` 不可强转回数组、重复读取返回同一实例、
以及改用只读包装后 `^1` 索引与 `Count` 仍可用（防回归）。

## 6. 明确拒绝的优化（附理由）

审查中出现的候选改动，经评估后**不予实施**。记录在此以免后续重复讨论：

| 候选改动 | 拒绝理由 |
|---|---|
| `FanCurve.Interpolate` 改二分查找 | 节点数由固件决定（量级 ≤ 10）。线性扫描更快且边界更少出错，O(log n) 在此规模无收益。属过度优化。 |
| `DeviceCapabilities` 改用 `ImmutableDictionary` | 会引入 `System.Collections.Immutable` 依赖，而 Core **零依赖是刻意设计**（纯契约层）。13–15 个键的复制成本可忽略。 |
| `PowerLimit` 改为 `struct` | 与可空语义组合后判等与装箱行为变复杂；限制对象只在配置变更时创建，GC 压力可忽略。收益不抵风险。 |
| 拆分 `OperationStatus` 枚举 | 会破坏 01 已交付、已被 02–07 依赖的契约稳定性。现有枚举语义无歧义。 |
| 让 `SensorReading` 保留 `with` 支持 | 与第 1 轮的不变量强制**直接冲突**：允许 `with` 等于重新打开任意字段改写，前一轮成果作废。 |
| 为 `MarkStale` 增加时间戳参数 | 采样时刻本就保存在每个读数内；新增参数会引入两处时间来源不一致的风险。 |

## 8. 剩余风险与移交事项

本轮已把契约层收敛到无明显缺陷，但以下事项**不属于**本轮范围，需明确移交：

1. **并发编辑风险（流程问题）**
   18:53–18:54 有另一进程修改了 `src/MsiControl.Core/Models/Capabilities.cs`
   并新建了 `MsiControl.Hardware.Msi` 工程与测试工程。本次优化**完整保留**了其成果
   （含 `ThermalFallback`、`PowerRange` 两个能力键及其证据注释）。
   但按任务书 §15.1，`MSI-Control.sln` 与 `Directory.Build.props` 应仅由整合负责人（07）修改。
   建议 07 明确并发窗口，或改用分支合并。

2. **能力基线与能力键的耦合点分散**
   并发编辑者已在 `CapabilityBaselineTests` 中加了「基线必须覆盖全部能力键」的测试；
   本轮的 `DeviceCapabilities.MissingKeys()` 提供了另一处启动自检。
   两处校验分属不同工程，建议 07 整合时统一，避免将来只改一处。

3. **硬件写入能力仍全部未验证**
   本轮只优化契约层。按 `docs/hardware-evidence.md`，除通用热区温度外
   **没有任何写入能力达到 `Verified`**——这是预期内的，属任务 03–06 的调查任务。
   契约层已把「未验证即禁用」变为默认安全方向，但真正的风险窗口在硬件适配阶段。

4. **`InvariantGlobalization` 的作用域**
   该设置定义在 `Directory.Build.props`，作用于构建产物所在进程。
   未来 `MsiControl.Desktop` 若需要正确显示数字，仍须自行确认区域性设置；
   契约层已通过显式 `InvariantCulture` 不依赖它。
