## 4. 修复记录

首轮构建与测试共修正 3 个问题，均记录在此以便后续任务复用：

### 4.1 测试项目缺 `using Xunit;`（224 处编译错误）

xunit v2 **不提供隐式 using**，`ImplicitUsings` 只覆盖 BCL。测试文件必须显式
`using Xunit;`。首轮因此报 224 个 `CS0246`。

> 后续任务新建测试文件时请直接带上该 using。

### 4.2 `new(null)` 被解析到 record 的拷贝构造函数（CS8625）

`PerformanceHardwareState.Unknown = new(null)` 触发
`CS8625: 无法将 null 字面量转换为非 null 的引用类型`。

根因：record 会自动生成拷贝构造函数 `PerformanceHardwareState(PerformanceHardwareState)`，
其参数类型为不可空引用类型。`new(null)` 与主构造函数形成歧义时被解析到拷贝构造函数。

**修法：改用命名参数** `new(ActiveStage: null)`。

> **这是本项目所有 record 的通用陷阱。** 当某个位置参数为可空类型、且实参为裸 `null` 时，
> 一律使用命名参数。

### 4.3 `FanCurve.TryCreate` 校验顺序不一致（1 个测试失败）

原实现先 `Validate(points)`（按给定顺序校验）再排序，导致乱序输入被判为非法，
与 `TryCreate_OrdersPointsAscending` 的预期矛盾。

这是一处真实的设计不一致，不是测试写错。修正为**先按温度规范化排序、再校验**：

- `Validate(points)` —— 保持原语义，校验**给定顺序**本身是否合法。
- `TryCreate(...)` —— 先排序、再校验，因此接受乱序输入。

两者语义已在 XML 文档中显式说明，避免后续任务误解。

### 本轮修复的实质缺陷（任务 02）

1. **主题应用无限递归 → 栈溢出（实机复现）**
   - 现象：首次冒烟测试以 `Stack overflow` 终止，进程无法进入消息循环。
   - 根因：窗口本身实现 `IThemeAware`，其 `ApplyPalette` 会回调 `ThemeApplier.Apply` 以刷新整棵树；
     `Apply` 遍历到根窗口时又调用 `ApplyPalette`，形成无限互相调用。
   - 修法：在 `ThemeApplier` 增加线程级重入深度计数，嵌套 `Apply` 直接返回。
     新增回归测试 `ThemeApplierTests`（构造实现 `IThemeAware` 的窗体并断言 `ApplyCount == 1`）。
   - 该缺陷**只在真实启动时暴露**，构建与单元测试均无法发现——说明实机冒烟测试不可省。
2. **`app.manifest` 与 `Application.SetHighDpiMode` 重复声明 DPI 感知**，触发 `WFAC010` 警告
   （破坏「0 警告」基线）。修法：DPI 感知改为只由运行时 API 提供，清单中移除 `dpiAware` / `dpiAwareness`。
3. **默认关闭的快捷键被记为警告日志**，把「用户主动关闭」误报为异常。
   修法：按 `Binding.Enabled` 区分 Info / Warning 级别。

#### 自查发现并修正的实质缺陷

1. **关闭按钮会留下无窗口的残进程（重要）**
   - 路径：`CloseToTray = false` 时点击标题栏关闭按钮。原实现在 `FormClosing` 中只发出退出请求、
     未设置 `e.Cancel`，因此即使用户在确认框选择「否」，窗体仍会被销毁——
     而 `ApplicationContext` 未设 `MainForm`，进程不会退出，形成「窗口已销毁、进程仍在托盘」的残状态，
     之后从托盘再打开会抛 `ObjectDisposedException`。
   - 修法：先 `e.Cancel = true` 再请求退出，由宿主决定；确认框选「否」时窗体保持存活。
     正常窗口与迷你窗口同样处理。
2. **托盘禁用项的原因提示永远不会显示**
   - 根因：`ContextMenuStrip.ShowItemToolTips` 默认为 `false`。
   - 后果：禁用项只有灰色，用户看不到任何原因——直接违反「不可用入口必须给出原因文案」。
   - 修法：显式开启工具提示，并在禁用项的**标题**中直接写入原因摘要（完整原因仍在工具提示里），
     因为并非所有系统设置都会显示菜单工具提示。
3. **派生只读属性被写入配置文件**
   - 现象：`settings.json` 中出现 `isComplete` / `hasModifier` / `isUsable`。
   - 影响：用户可能手工修改这些字段并以为会生效，实际由其他字段推导。
   - 修法：对三者加 `[JsonIgnore]`，并新增测试断言文件内不出现这些名字。
4. **开发环境下保存设置会把开机启动静默关闭**
   - 路径：`!StartupRegistration.CanRegister` 时复选框被强制置灰为未勾选，
     保存时把 `false` 写回，覆盖原有 `true`——环境限制被当成用户意图。
   - 修法：环境不可写时保留存储值，并在诊断区显示「设置意图 vs 注册表实际状态」。
5. **首次运行不落盘设置文件**
   - 现象：设置界面有值，但磁盘上没有 `settings.json`，用户无法查看/手改。

### P2 补充：对照目标图的实机截图修正（2026-10-17 上午）

叶哥实机截图与目标设计图对照后，发现并修复三处布局缺陷（均为实机渲染才能暴露的问题）：

1. **卡片标题跑到卡片底部**：WinForms 停靠按 z-order 从后往前处理，
   Card 内先加 header 后加 content，导致 content 先贴顶、标题被挤到卡片下边缘。
   已调换添加顺序（content 先入、header 后入）。
2. **状态条悬浮并与 App bar 重叠**：statusStrip（CreateRow 产出）从未设置 Dock=Top，
   以默认位置悬浮在客户区 (0,0)，徽标压住品牌标与标题。已显式 `Dock = DockStyle.Top`。
3. **状态徽标坍缩成无字小块**：StatusPill 原为「UserControl + 内部 Dock=Top 的
   FlowLayoutPanel」，在流式父容器中宽度计算成环（父宽等子宽、子宽又等父宽）。
   已重构为直接继承 FlowLayoutPanel，AutoSize 由流式布局自生。

## 2026-10-31 第十八轮：主页面滚动位置复位缺陷修复与验证

- **现象**（叶哥反馈）：主页面向下滚动后，页面会自己跳回上方。
- **定位**（插桩 + 跨进程探测，非推测）：
  - 采样数据每秒改写 `MetricTile` 的 AutoSize 文本，触发「标签 → 瓷砖 → 网格 → 滚动宿主」
    的嵌套布局；停靠布局成型前还会把滚动宿主临时撑成整个客户区高度（878 px = 795 + 状态带 48 + 状态栏 35）。
  - 这两种情况都会让 `ScrollableControl` 按**瞬时**滚动范围重算滚动条，把当前偏移钳制成
    57 px（= 内容 935 − 瞬时客户区 878）；范围恢复后不再还原 → 内容永久停在 57。
  - 判别证据：把窗口高度改成 900/760/640/560 后，复位目标恒为 57（与视口高度、内容高度无关）；
    偏移 ≤ 57 时不触发；复位瞬间的调用栈为 `Label.OnTextChanged → ResumeLayout → 宿主 OnLayout`。
- **修复**：
  1. `MainForm.ApplyWithLayoutSuspended`：整帧刷新（读数、状态徽标、扩展传感器）合并为一次布局，
     级联结束后延迟对齐一次滚动状态。
  2. `ScrollHostPanel`：记录用户意图偏移（仅用户滚动时更新），在 `OnLayout` 与
     `OnClientSizeChanged` 后写回被钳制的偏移；并用 `SetScrollInfo` 把滚动条自身的
     `SCROLLINFO` 校正回真实范围（只在取值不一致时写）。
- **验证**：`scripts/verify_scroll_position.py`（滚到 140 px 后观察 5 s：位置恒 140，帧间平均差 0.33）
  与 `scripts/verify_scroll_interaction.py`（逐行/翻页/缩放窗口后位置不越界、不复位），两项 PASS。
  阴性对照：临时关闭写回后同一脚本 FAIL（偏移 140 → 57，帧间平均差 17.39，内容确实整屏位移）。
- **回归**：解决方案 Release 0 警告 0 错误；全量测试 1060/1060 通过。
- **残留**（如实记录）：滚动条拇指仍有 <1% 采样（约每 10 s 偶发一帧）被系统推送一次中间值；
  内容位置不受影响（模型与服务端偏移均为用户值）。彻底消除需接管滚动实现（自绘 VScrollBar）。

## 2026-11-01 第十九轮：主页面「鬼畜刷新」定位与修复

- **现象**：主页面空闲时界面持续闪动/重绘，操作时会卡顿；最小化后仍见进程 CPU 占用偏高。
- **量化基线**（插桩：进程内 WM_PAINT 计数 + 线程 CPU 采样 + 分段计时）：
  空闲 **UI 线程 25%、进程 12%**；每秒 WM_PAINT 19–29 次，其中**分段按钮 16 次/秒**
  （每组每秒各被重绘一遍）；`ApplyWithLayoutSuspended` 整帧耗时 **140–170 ms**。
- **根因三条**：
  1. **布局挂起挂错层级**：只 `SuspendLayout()` 了窗体。`SuspendLayout` 只停住被调用控件自身，
     父级仍会被逐个要求重排，于是每秒 10 条文本变更仍一路「瓷砖 → 网格 → 卡片 → 内容栈」
     重排到底，单帧 140–170 ms。改挂内容栈根（`_stack`）后同帧降到 **6.8 ms**（+10 ms 合并布局）。
  2. **样式每秒无条件重刷**：`SegmentedGroup.SetActive` 每次调用都把整组按钮的
     `FlatStyle/FlatAppearance/BackColor/ForeColor/圆角描边` 重写一遍，而这些 setter
     全部会 `Invalidate()`；且**悬停色写在底色之前**——`ButtonBase` 在 `BackColor` 变化时会清空
     `FlatAppearance` 的 MouseOver/MouseDown 颜色，导致悬停色每秒被重设一次、每秒再重绘一次。
  3. **同值重复写入**：`MetricTile.SetValue`、`StatusPill.SetValue` 每秒重新赋同样的文本/颜色/
     ToolTip，触发多余的重绘与布局。
- **修复**：
  - `MainForm.ApplyWithLayoutSuspended`：挂起改到 `_stack`（内容树根），整帧只做一次合并布局。
  - `SegmentedGroup`：`Style` 逐项比较后再赋值；新增 `ApplyHover` 放到**底色之后**执行。
  - `MetricTile` / `StatusPill`：值、备注、语气、待生效标志均未变时直接返回。
- **验证**：`scripts/verify_refresh_behavior.py`（空闲 CPU + 帧变化率 + 滚动后重绘），连跑 3 次全 PASS：
  空闲 **UI 线程 1.3–3.1%、进程 3.8–6.3%**；帧变化 **1.0–1.2 次/秒**（与 1 s 刷新间隔一致）、
  **无大面积整窗重绘**；分段按钮每条样式写入仅发生在启动那一次（196 条，之后为 0）。
- **副作用检查**：`verify_scroll_position.py`、`verify_scroll_interaction.py` 连跑均 PASS（内容不位移，
  偶发 1 个原生滚动条瞬态样本，属已记录残留）；解决方案 Release 0 警告 0 错误；全量测试 **1060/1060**。

## 2026-11-01 第二十轮：主页面「持续抽动」根因定位与滚动机制重构

- **现象**（叶哥第二轮反馈）：上一轮修完后仍有持续抽动。实测确认：页面滚到某处后，
  偏移会被**每秒一次**改写（140/146 → 57），我们的写回逻辑把它拉回，于是形成
  「每秒来回一次」的可见抽动。上一轮的「事后写回」是把它变成可重复循环，不是修复。
- **定量证据链**（插桩 + 跨进程探测，全部实测）：
  1. `RESTORE cur=57 -> 140` 每秒出现一条，连续 10 条不停；
  2. 强设 `SetScrollInfo(nPos=146)` 后读回仍是 57 → 系统内部范围只有 852，
     而非当时的 `nMax=940`（说明范围与位置来自两次不同的范围计算）；
  3. `ClientSize` 稳定 795、`DisplayRectangle` 稳定 941，钳制与「尺寸变化」无关；
  4. 焦点 / 滚动 / 滚轮消息在滚动后均无记录 → 不是 `ScrollControlIntoView`、不是滚动事件；
  5. `_stack`（内容栈）在刷新瞬间会出现一次偏小高度（935 → 852，少 83 px），
     与 `852 − 795 = 57` 完全吻合。
- **根因**：`ScrollableControl.AutoScroll` 把「直接子控件边界并集」当滚动范围，
  每次布局按瞬时值重算并顺手钳制当前位置。内容栈是 `AutoSize` 表格，每秒刷新都要
  重新量高，其中间态偏小 83 px；一旦撞上范围重算，位置就被写成
  `瞬时高度 − 客户区高度 = 57`。该值**与内容高度、视口高度都无关**（改窗口高度仍是 57），
  且范围恢复后不会自愈。所有「事后写回」都只能把它变成每秒循环。
- **修复（结构性，非缓解）**：
  1. `ScrollHostPanel` 改为**自管滚动**：`AutoScroll = false`，内容放在尺寸由本类维护的
     承载面板里，滚动条换成独立的 `VScrollBar`（`SetWindowTheme` 保留深色变体）；
     偏移只由 `SetOffset` 修改，范围只由内容高度高水位决定，WinForms 再无改写入口。
  2. 承载面板宽度与滚动条可见性在同一轮内两轮收敛（先定宽量高，再让出滚动条宽度重设）。
  3. `MainForm.ApplyWithLayoutSuspended` 不再在窗体层 `ResumeLayout(performLayout: true)`
     （那次重排会让 `Dock=Fill` 的宿主短暂拿到全客户区高度），只重排内容树。
  4. `ScrollHostPanel` 抑制程序写 `VScrollBar.Value` 时回抛的 `Scroll` 事件，
     避免「范围变化 → Value 被钳 → 回写用户意图」的反馈环把位置清零。
  5. 展开 / 收起面板后由 `RecomputeExtent` 显式重算范围（允许变小），平时只取高水位。
- **验证**：新增 `scripts/verify_scroll_stability.py`（取代已失效的两个旧脚本），
  四个用例：滚轮到底后 8 秒偏移分布必须只有一个取值、内容区无整屏位移、中间位置静止、
  缩放窗口后不越界不被拉回顶部。**连跑 5 轮全部 PASS**：
  偏移分布恒为 `{146: 41~44}`（此前为每秒 140↔57 往返）。
  折叠展开复测：940 → 1102（滚到底 308，4 秒恒定）→ 收起 934（140，4 秒恒定）。
- **回归**：`verify_refresh_behavior.py` PASS（空闲 UI 线程 1.25%、进程 5.0%，
  帧变化 1.0–1.2 次/秒，无大面积重绘）；解决方案 Release 0 警告 0 错误；
  全量测试 **1060/1060** 通过。
- **说明**：外部脚本模拟「拖动滚动条滑块」会让原生 SCROLLBAR 进入无捕获的拖拽态、
  位置持续漂移，属注入方式干扰，故自动判据只覆盖滚轮与缩放；拖动由人工验证。
