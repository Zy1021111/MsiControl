## 1. 定位与边界

本任务负责**性能与功耗**：五档性能配置、CPU 持续/短时功耗上限、CPU 睿频上限、GPU 功耗上限、
GPU 兼容节能策略，以及与 MSI 固件性能场景的协调。

| 属于本任务 | 不属于本任务 |
|---|---|
| CPU 功耗、CPU 睿频上限、GPU 功耗上限 | 风扇曲线与校准（04） |
| 五档配置的编辑、校验与应用计划 | 温度与功耗**读数**（03） |
| 功耗限制生效性的判定规则 | 显卡模式切换（06） |
| 第三方工具（XTU / Afterburner）共存检测 | 窗口、托盘、设置界面（02） |
| 固件性能场景写入门控 | 串行调度与请求优先级（07） |

**硬边界**：本任务**不直接操作窗口**（提示词 §四 纪律 11），**不自己定时争抢硬件设置**
（同 纪律 9），**不修改 `MsiControl.Core`**、`Hardware.Msi/Transport`、`Discovery`、`Capabilities`
（同 纪律 1、10）。

## 3. 核心机制

### 3.1 可写范围：「不静默替换」的落点（任务书 §8.3）

```csharp
var range = LimitRange.Known(35m, 90m, 5m, "Get_Range 返回值");     // 已知
var range = LimitRange.Unknown("Get_Range 传 null 被 WMI 拒绝");    // 未知（必填原因）

var verdict = LimitSupportEvaluator.Evaluate(PowerLimit.Custom(20m), range);
// verdict.Verdict            == BelowReportedMinimum
// verdict.CanApplyRequestedValue == false      ← 不按原值下发
// verdict.RequiresFallback    == true
// verdict.NearestSupportedValue == 35m         ← 仅作**建议**，不自动采用
```

三种拒绝文案分别写明「不会按该值下发」「不会静默替换」「不会静默截断」，
并使用户能看到实际范围。**范围未知时既不假定受支持，也不假定不受支持**，判定为 `RangeUnknown`。

### 3.2 五档配置与逐项应用计划（任务书 §8.1、§8.2、§8.5）

- 默认值**一律取自 `PerformanceProfileCatalog`**，本模块**不另建数值表**
  （`SettingKeyConsistencyTests.Defaults_MatchTaskBookSection81` 直接对任务书 §8.1 的六个数值断言）。
- 原生上限一律用 `LimitMode.Native`，计划中呈现为**文字「原生上限」**而非数字；
  `BuildPlan_NativeLimitsBecomeRestoreNative_NotZeroOrInfinite` 断言不含 `9999` / `-1`。
- 每档独立保存 7 项（CPU 持续 / 短时 / 睿频、GPU 上限、GPU 节能策略、CPU 曲线、GPU 曲线），
  曲线引用由 `PerformanceSettings.CpuCurve` / `GpuCurve` 承载（与任务 04 的衔接点，不另建档位配置）。
- 计划把配置摊平成**逐项请求**，因此每一项都能独立门控、独立下发、独立读回、独立报告状态。

下发前自检 `ValidateBeforeApply` 在 Core 的 `PerformanceSettings.Validate()` 之上追加一条：
**「GPU 上限为原生上限却携带替代节能策略」属于自相矛盾**，必须先明确目标值。

#### 曲线引用与 Windows 电源策略（§8.2 的两个衔接点）

1. **每档的 CPU / GPU 风扇曲线引用**由 `PerformanceSettings.CpuCurve` / `GpuCurve` 承载
   （类型由任务 01 在 Core 中提供），**不进入本模块的应用计划**：
   曲线的校验与下发属任务 04（`IFanHardware`）。本模块只负责把「某一档」与「该档的两条曲线」
   绑定在一起，并保证档位切换时不丢失引用（`ValidateBeforeApply` 会检出曲线绑到错误通道的配置）。
   因此 04 与 05 **不会各建一套档位配置**（提示词 §备注明确要求）。

2. **Windows 电源策略**：本模块**不修改用户的 Windows 电源计划**，也不设置
   「处理器最大状态百分比」。理由有两条，均来自任务书本身：
   - §8.2 明确**禁止**用 Windows CPU 百分比冒充精确功耗限制，用电源计划表达「性能档」
     正属于被禁止的表达方式；
   - 修改用户的电源计划会与 MSI 固件场景产生**未经验证**的相互作用，且超出本项目授权范围
     （§1 原则 9：不自动改变系统级设置；§四 纪律 8）。
   在固件场景与 Windows 电源计划之间做协调（若确有需要）属任务 07 的自动策略范围，
   且必须先取得实测依据。

#### 高性能与狂暴：主要由散热配置区分

两档在功耗上均为原生上限，默认配置**完全相同**
（`SettingKeyConsistencyTests.HighPerformanceAndExtreme_DifferOnlyByThermalConfiguration` 逐项断言
CPU 持续 / 短时 / 睿频 / GPU 上限均相等）。

本机**尚未取得「两档存在额外性能能力差异」的任何证据**，因此**不虚构增强能力**、
不预设 APEX / Surge 之类增强模式；两档的实际差别由**各自独立的风扇曲线**（散热配置）表达，
曲线本身的编辑与下发属任务 04。狂暴**不自动开启强冷**——强冷接口在本机未定位，能力为 `Unknown`。

### 3.3 GPU 替代策略（任务书 §8.3 五点要求的逐条落实）

| 任务书要求 | 落实方式 |
|---|---|
| 显示支持范围 | `LimitRange.Describe(unit)` 输出范围、步长与**来源** |
| 不静默替换参数 | 判定与规划都不改写目标值；替代值只在 `GpuEcoFallback` 中显式出现 |
| 提供经过验证的兼容节能策略 | 仅在本机已报告下界时才生成；范围未知时**不给**替代值（不猜下界） |
| 明确不保证精确达到目标瓦数 | `GpuEcoFallback.Limitation` 为必填，且由规划器写入该句与「不代表实际耗电」 |
| 不扩展为超频 / VF 编辑 | 限制文本内明示「策略范围不含超频与 VF 曲线编辑」 |

### 3.4 限制生效性判定（任务书 §8.5）

```csharp
var verdict = LimitVerification.Verify(new LimitVerificationInput(
    SettingKey: PerformanceSettingKeys.CpuLongTerm,
    RequestedValue: 60m,
    ReadBackValue: 60m,              // 主证据
    Load: LoadCondition.EffectiveLoad,
    ObservedPackageWatts: 58m,       // 旁证
    ObservationWindow: TimeSpan.FromSeconds(120)));
```

判定优先级与结论：

| 情形 | 结论 |
|---|---|
| 原生上限（无自定义值） | `NotAttempted`——不产生「限制生效」的断言 |
| 读回值与请求值一致（容差内，默认 ±0.5） | `ConfirmedByReadBack`——**唯一**可判生效的情形 |
| 读回值不一致 | `ReadBackMismatch`——已确认未按请求生效 |
| 无读回值 + **低负载** | `InsufficientEvidence`——**低负载功耗低于目标不是证据** |
| 无读回值 + 有效负载 + 实测持续超出（默认 +5%） | `ObservedExceedsRequested`——未生效 |
| 无读回值 + 其他 | `UnverifiableByReadBack`——未确认，**不得宣称生效** |

读回值一致但实测瞬时超出时，判为**已确认**，并在备注中说明这是时间窗口内的瞬时偏差，
同时写明「不能承诺每次采样都低于设定值」。详细论证见 `docs/限制生效性验证报告.md`。

### 3.5 第三方共存（任务书 §11、§4.1 A8）

- 检测清单只登记**已确证安装**的两个程序：Intel XTU（进程 `XTU` / `XTU3SERVICE`）、
  MSI Afterburner（进程 `MSIAfterburner`）；不凭猜测扩充。
- 重叠项按本任务负责范围声明：XTU → `cpu.longterm` / `cpu.shortterm` / `cpu.turbo`；
  Afterburner → `gpu.limit`。
- **「该程序在运行」不等于「设置已被覆盖」**：结论文案明确写出这一区分，
  并要求以「读回值与请求值不一致」作为被覆盖的证据。
- 边界说明固定包含：不修改、不停止、不卸载、**不通过无限循环写入争夺控制**；建议用户在其设置
  中关闭重叠项的开机自动应用。
- 探测失败（权限、进程退出）按「未运行」处理，**不阻断**性能设置流程。

### 3.6 应用用例与取消语义（任务书 §16、约定 §6）

`PerformanceApplication.ApplyAsync` 的顺序为：配置自检 → 生成计划 →（有探测时）冲突检测 →
调用硬件 → 结果合规自检。配置自检不通过时**不向硬件下发任何内容**，
并返回一个带原因的 `Failed` 结果（保证 `ControlResult.Settings` 非空）。

取消标记原样传递给硬件实现，本类型**不吞 `OperationCanceledException`**；
写入后的读回义务由实现方承担（本机因协议未验证尚无写入，故也无读回）。

## 4. 硬件适配层：两道闸门

`Ms15M3PerformanceHardware.ApplyAsync` 对每个设置项依次判定：

```text
① 能力闸门：_capabilities.AllowsWrite(CapabilityKeys.X) ?
     否 → Unsupported（附：当前等级 + 该能力的证据/依据原文）
     是 ↓
② 协议闸门：PerformanceProtocolStatus.DataLayoutVerified ?
     否 → Failed（附：开放写入的三条前置条件）
```

本机的实际结果（实机运行，见 `docs/hardware-evidence.md` §11.4）：

| 设置项 | 能力键 | 当前等级 | 实机结果 |
|---|---|---|---|
| `stage` | `firmware.scenario` | `Detected` | `Unsupported` + 依据 |
| `cpu.longterm` / `cpu.shortterm` | `cpu.power` | `Detected` | `Unsupported` + 依据 |
| `cpu.turbo` | `cpu.turbo` | `Unknown` | `Unsupported` + 依据 |
| `gpu.limit` | `gpu.power` | `Detected` | `Unsupported` + 依据 |

每一项都记录了**请求值**（含「原生上限」文字），整体状态由 `ControlResult.From` 归并，
`ControlResult.Validate()` 返回 0 个问题。**实机运行时不会产生任何硬件写入。**

### 4.1 为什么 `ReadAsync` 恒返回 `Unknown`

本机实测：`Data` 传 `null` 时 5 个 `Get_*` 全部被 WMI 层以 `0x80041008`（无效的参数）拒绝，
调用未到达固件，无任何返回数据。`Data` 的结构未知，把原始字节流解释成瓦数属于
「猜测数值含义」（任务书 §四 纪律 3）。

因此 `ReadAsync` 的诚实结果是 `PerformanceHardwareState.Unknown`：**不填任何读回值**。
若强行填入推测值，`LimitVerification` 会据此把限制误判为已生效——这正是本项目
最需要避免的「虚假成功」。协议验证后此方法才应返回真实读回值。

`LastProbe` 暴露最近一次探测报告，供诊断与证据采集使用；**不参与任何控制决策**。

## 6. 接入指引

### 任务 07（协调器与整合）

```csharp
var capabilities = CapabilityBaseline.ForDevice(device);
IMsiAcpiTransport transport = new WmiMsiAcpiTransport();
var hardware = new Ms15M3PerformanceHardware(transport, capabilities);

var application = new PerformanceApplication(
    hardware,
    new WindowsProcessPresenceProbe());      // 不需要冲突检测时传 null

// 由协调器在自己的串行队列内调用；本组件不自建队列、不定时。
var outcome = await application.ApplyAsync(settings, cancellationToken);
```

- `outcome.ConfigurationRejected` 为真时不要继续任何后续步骤；
- `outcome.IsCompliant` 为假说明出现了「无依据的成功」，必须按缺陷处理；
- `outcome.ThirdPartySummary` 可直接展示给用户；
- **`ReadAsync` 每次会发起多次 WMI 调用**（`Get_Power` / `Get_Range` / `Get_Device` / `Get_AP` / `Get_PE`），
  **不要按采样频率（每秒）调用**；只应在需要刷新性能状态时调用，并复用其结果；
- 电源事件（拔电 / 插电）与启动恢复的策略**属 07**：本模块只提供「判定与应用」。

### 任务 02（界面）

- 参数表的数据来源仍是 `PerformanceProfileCatalog`（**软件配置目标，不是硬件读回值**）。
- 渲染逐项结果时请按键对齐 `PerformanceApplyOutcome.Plan` 的 `Key`，
  并展示 `SettingResult.Requested`（请求值）与 `ReadBack`（读回值，本机为「无」）。
- 禁用原因请使用 `SettingResult.Message`（已含能力等级与证据原文），不要自行编造文案。

### 任务 03（监控）

- 本模块**不读取**温度与实时功耗：判定所需的 `ObservedPackageWatts` 应由 03 提供。

## 7. 已知限制

| 限制 | 说明 |
|---|---|
| 本机无任何写入能力 | 两个闸门均未通过；写入路径**刻意未实现**（无协议依据） |
| 读回值不可得 | `Data` 结构未知 → `ReadAsync` 只能返回 `Unknown` |
| 生效性未做实测 | 需要「正确协议 + 用户配合构造持续负载」，见 `docs/限制生效性验证报告.md` |
| 范围未知 | `Get_Range` 未能返回范围 → `LimitRange.Unknown`，替代策略暂无输入 |
| 锁定 / 覆盖状态**不可判定** | 「是否被固件锁定」「是否被 XTU / Afterburner 覆盖」都**必须依赖读回值**才能判定。本机无读回通道，因此这两项属**未获取证据**，不得据此声称已锁定或已被覆盖（依据登记于 `PerformanceProtocolStatus.UnverifiedItems`）；界面在无法判定时必须显示「未确认」，不能替用户下结论 |
| 设置项标识在硬件层重复登记 | 为保持依赖方向（Hardware 只依赖 Core），硬件层用字面量登记，由 `SettingKeyConsistencyTests` 锁定一致性 |
| 不提供 UI | 按纪律 11，界面由 02 负责；本模块只提供领域行为与结果数据 |
| 不修改 Windows 电源计划 | 见 §3.2；用电源计划表达性能档属任务书 §8.2 禁止的做法 |
| 风扇曲线不在本模块下发 | 曲线引用随档位保存，下发属任务 04（`IFanHardware`） |

## 9. 档位功耗目标的持久化（v2，2026-10-30 增补）

> **前置更正**：§7「本机无任何写入能力」与「生效性未做实测」是任务 05（WMI 通道）当时的真实结论，
> 已被 `docs/hardware-evidence.md` §26 推翻——CPU 功耗墙经 MSR 0x610 实测可写、可读回、
> 切档不被固件覆盖；GPU 侧三条通道（NVML v1/v2、`nvidia-smi -pl`）均返回 NOT_SUPPORTED。
> 以 HWE §26 为准，本节只补「目标如何持久化」。

### 9.1 存什么

`settings.json` 的 `settings.stageTargets` 保存五档的 CPU 功耗目标：

```json
"stageTargets": [
  { "stage": 0, "cpuWatts": 10 },
  { "stage": 1, "cpuWatts": 50 },
  { "stage": 2, "cpuWatts": 60 },
  { "stage": 3, "cpuWatts": null },
  { "stage": 4, "cpuWatts": null }
]
```

- `stage` 是 `PerformanceStage` 的数值（0 节能 / 1 安静 / 2 平衡 / 3 高性能 / 4 狂暴）；
- `cpuWatts` 为 `null` 表示**原生上限**，加载后映射为 `PowerLimit.Native`，
  **绝不以 0 或极大数表达无限**（Core 的构造层会直接拒绝）；
- 只存 CPU 持续/短时（界面一个输入框同写两者）。GPU 功耗与睿频上限**不存**：
  本机无写入通道，存了只会得到「保存了却永远不下发」的假配置。

### 9.2 何时写

- 主窗口「详细编辑」的性能表提交（回车）后立即落盘，写全五档快照；写失败时界面明示
  「本次运行内有效，重启后会回到默认值」，内存不做「假保存」。
- 加载时 `AppSettings.Normalize` 对目标做防御性校验：未登记档位、重复项、
  `<= 0` 或 `> PowerLimit.MaxCustomWatts` 一律**丢弃并回退该档默认值**（不夹紧、不猜测）。
- 迁移：`settings.json` 的 `schemaVersion` 由 1 升到 2，`SettingsV1ToV2Migration` 只补空表——
  v1 从未持久化过档位目标，不存在需要搬运的历史数据；缺这步会让 v1 文件被判定「无法安全升级」
  而整体回退默认，连带丢掉窗口位置与快捷键。

### 9.3 何时生效

目标只在**切换档位**时下发（`ControlCoordinator.ExecutePerformanceStageAsync`）；
编辑本身不写硬件，这是刻意设计，避免边输边写。启动时 `Program` 把已保存目标注入协调器，
因此重启应用后再点同一档位，下发的是用户保存的值，而不是默认表值。

### 9.4 与配置档（ConfigProfile）的关系

`ConfigProfile` 仍是**跨设备导入导出**的载体（含设备标识与整档校验），与本节的
「本机持久化」是两件事：前者面向迁移与分享，后者面向「关掉程序再打开还在」。
两者的字段语义必须一致，否则导出再导入会静默改写目标。

## 10. 性能模式的人工确认语义（2026-10-31）

本节回答三个问题：**什么时候允许改档、退出时档位去哪了、下次启动按什么恢复。**
规则由用户（叶哥）明确指定，代码与测试均已按此收紧。

### 10.1 运行中：不自动改档

- 供电变化（拔电/插电）**不再**自动切到节能或恢复原档：`PowerSupplyPolicy` 仍会算出
  建议动作并写日志，但 `ApplicationHostOptions.AutomaticStageSwitchingEnabled` 默认
  `false`，`ApplicationHost.ApplyPowerDecisionAsync` 在门后直接返回，**不下发任何写入**。
- 配置档启动恢复（`StartupRestorePolicy` + `ILastAppliedConfigSource`）同样只在
  `AutomaticStageSwitchingEnabled = true` 时才真正提交；默认只记录判断依据。
- 唯一未被关闭的自动写入是「恢复上次用户确认过的档位」（§10.3），它恢复的是
  用户自己确认过的值，不是策略推断值。

### 10.2 用户主动退出：写回固件基准场景

- 触发条件：**本次会话内本软件写过性能场景**（用户手动切档成功，或启动恢复写成功）。
  若整场会话没碰过档位，退出时不写 0xD2——否则就是一次用户没要求的自动变更。
- 写入内容：**只写 EC 0xD2**（`IScenarioRestoreChannel.ApplyScenarioOnlyAsync`），
  目标是 `PerformanceShiftMap.FirmwareDefaultStage`（平衡，comfort/0xC1）。
  **不写 MSR 0x610、不动风扇模式与曲线**：退出恢复的语义是「撤销本软件对场景的改动」，
  不是「再应用一次某档配置」。
- 等待上限 8 秒（`DesktopApplicationContext.ExitStageRestoreTimeout`）；超时或失败
  如实记日志，不宣称已恢复。
- 适配层未实现 `IScenarioRestoreChannel` 时返回 `Unsupported` 并说明原因，
  不降级为整档应用。

### 10.3 再次启动：恢复上次用户确认的档位

- 记录位置：`settings.json` 的 `lastConfirmedStage`（`AppSettings.LastConfirmedStage`，
  schema **v3**；`SettingsV2ToV3Migration` 只置空，历史文件因此不会被判「无法升级」）。
- 写入时机：只由「用户手动切档且 `stage` 项读回成功」这条路径写入
  （`ApplicationControlSink.StageConfirmed` → `ShellContext.TryRecordConfirmedStage`）。
  自动策略、启动恢复、退出恢复**都不改**该字段。
- 读取时机：`Program.StartStageRestore` 在 `host.Start()` 之后后台调用
  `ApplicationHost.RestoreUserConfirmedStageAsync`，以 `Automatic` 来源提交
  （因此不会覆盖仍在排队的手动请求）。
- 三道拒绝条件（均不写入并写明原因）：无记录、本机设备未识别、档位在本机无已证实编码。

### 10.4 三态预期行为

| 状态 | 性能场景（EC 0xD2） | 设置文件 `lastConfirmedStage` |
| --- | --- | --- |
| 运行中（用户点档位并读回成功） | 写入用户选择的编码 | 更新为该档位 |
| 运行中（拔插电源、唤醒、时间流逝） | **不变** | 不变 |
| 用户主动退出（本会话写过场景） | 写回 0xC1（平衡） | 不变（仍是用户确认值） |
| 用户主动退出（本会话未写场景） | 不变 | 不变 |
| 下次启动（有记录且设备已识别） | 写入记录的档位 | 不变 |
| 下次启动（无记录/设备未识别） | 不变 | 不变 |
