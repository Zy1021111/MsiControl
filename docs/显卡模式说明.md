## 3. 架构与接入方式

```text
Desktop（02，已有 UI：主窗口 / 迷你窗口的显卡按钮与「实际显卡模式」状态条）
   ↓  ShellContext.Control.RequestGraphicsModeAsync(mode)   ← 02 定义的 IControlRequestSink
Application 协调器（07 待实现，负责串行写入与结果发布）
   ↓
GraphicsHardwareService : IGraphicsHardware          ← 本任务
   ├─ GraphicsSwitchPolicy      纯策略：能力门控 → 拓扑 → 支持性 → 风险三态
   ├─ GraphicsModeInference     拓扑 → Current / Supports / 外接屏信息
   ├─ GraphicsTopologyProbe     只读：root\CIMv2 + root\WMI + CfgMgr32
   └─ IGraphicsModeWriter       写入方；当前为 UnsupportedGraphicsModeWriter（无可用路径）
```

**写入方只在「允许且真的需要落盘」（`GraphicsSwitchDecision.RequiresWrite`）时才被调用。**
拒绝项与空操作（已是目标模式）直接回报结论，不会产生多余的写入尝试。
在当前设计下该分支**生产环境不可达**（见 §4.2），只为将来接入真实写入预留。

**任务 07 的注入方式：**

```csharp
IGraphicsHardware graphics = new GraphicsHardwareService(
    new GraphicsTopologyProbe(),                 // 只读显示拓扑探测
    CapabilityBaseline.ForDevice(device),        // 能力门控（graphics.mode 现为 Unknown）
    writer: null);                               // 省略即「本机无可用切换路径」
```

`GraphicsHardwareService` 不含任何定时器、事件或启动钩子，**不会被自动调用**，
满足任务书 §9.1「不在启动与供电变化时自动切换显卡模式」。

## 4. 关键语义（评审要点）

### 4.1 当前模式是「拓扑推断」，不是 MUX 直读

本机没有任何可读取 MUX / 显卡模式的状态接口，因此 `Current` **由已确证的显示拓扑反推**：

| 拓扑形态 | 推断结果 |
|---|---|
| 内置屏由**独显**驱动 | `Discrete` |
| 内置屏由**核显**驱动，且存在**由独显驱动的外接屏** | `Hybrid` |
| 其余（无内置屏、内置屏驱动方未知、或核显驱动内置屏但独显无输出） | `null`（**不猜**） |

第三行是刻意的：核显模式与「未接外接屏的混合模式」在拓扑上不可区分，
用默认值冒充已知会违反任务提示词 §七。

### 4.2 支持性标志只覆盖「已观察在生效」的模式

`SupportsIntegrated` / `SupportsHybrid` / `SupportsDiscrete` 仅当该模式**被观察到正在生效**时为真。
未观察到的模式没有任何切换路径证据，一律按不支持处理——
不臆测「同系列机型支持」（任务书 §2.2）。

与 `graphics.mode = Unknown` 共同构成**双重保守**：即便硬件确实支持某模式，
只要本程序无法切换，界面也不会开放写入。

> **由此产生的一个可预期后果：**在当前严格推断规则下，「允许且需要写入」这一分支
> **在本机不可达**——受支持的模式只有当前模式，而切到当前模式属于空操作。
> 这不是缺陷，而是「没有切换接口」的必然推论。为让写入方委派逻辑仍得到回归覆盖，
> `GraphicsHardwareService` 提供了一个 `internal` 构造重载用于注入受控状态
> （`InternalsVisibleTo` 仅对测试工程开放），并在测试中显式标注「生产环境不可达」。

### 4.3 外接屏风险是三态，不是布尔

`GraphicsHardwareState.WouldDisconnectExternalDisplay(target)` 返回 `bool?`：

- `true` → 会断开 → 策略**拒绝**切换
- `null` → 拓扑未确认 → 策略**拒绝**（**不得按「无风险」处理**，任务书 §9.2）
- `false` → 不会断开 → 允许继续

`GraphicsSwitchPolicy` 在拓扑未确证时（`topologyKnown == false`）**短路拒绝**，
不进入风险判定，避免「未知」被误读为「安全」。

### 4.4 不产生虚假成功

- `RequestModeAsync` 在能力未达 `Verified` 时返回 `Unsupported` 并附依据；
- 目标模式没有可切换路径证据时返回 `Unsupported`；
- 默认写入方 `UnsupportedGraphicsModeWriter` 不做任何硬件访问，恒返回 `Unsupported`；
- 空操作（已是目标模式）不委派写入方，直接回报「无需切换」并附确认依据；
- 所有分支的结果均通过 `ControlResult.Validate()`（实测 0 个问题）。

### 4.5 重启方式不笼统表述

策略在允许切换时给出的说明**不写「需重启」了事**，而是明确：
「写入后生效需要重启设备；具体为『普通重启』还是『S5 关机再开机』，取决于实际固件路径，
须由写入方按实测结果给出」。本机尚未取得该证据，故不替用户断言（任务 06 提示词 §三.3）。

### 4.6 Core 保守规则的沿用（不改写契约）

`GraphicsHardwareState` 的规则是「外接屏依赖独显时，**任何非独显直连的目标**都标为有风险」，
其中**包含混合模式**。该规则偏保守——混合模式下外接屏实际仍由独显驱动、未必断开。
`GraphicsHardwareState` 属任务 01，**本任务不改写契约**，仅在该规则的边界上
用测试记录其语义（`GraphicsModeInferenceTests`）。

> 若 01 / 07 认为应细化（例如「目标为混合且外接屏走独显 ⇒ 无风险」），
> 需由 01 评估影响面后变更；本任务不擅自修改 `src/MsiControl.Core`。

## 5. 显示拓扑与用户场景（任务书 §9.2）

| 项目 | 实测 |
|---|---|
| 内置屏 | `DISPLAY\AUO7DB2\...`（AUO 面板 2560×1600），父设备 = **Intel 核显** |
| 外接屏 | `DISPLAY\SAC2563\...`（型号 `G4Q`），输出技术 = `10`（DisplayPort 外接），父设备 = **NVIDIA 独显** |
| 雷电 / USB4 | 存在 `USB4 主机路由器` |

**判定方法**（可复现，不依赖线缆名称）：

1. `WmiMonitorConnectionParams.VideoOutputTechnology == 0x80000000` → 内置屏；其余已知值 → 外接屏。
2. 显示器在 PnP 树中的**父设备**即驱动它的 GPU，由 `CfgMgr32` 查询。
3. GPU 类别按 PCI 厂商 ID 判定（`8086`→核显，`10DE`→独显；AMD 按型号名，无法确定返回未知）。

**对用户的实际含义：**

- 切换到「核显模式」会使外接屏断开 → 策略会拒绝，并说明原因。
- 即使在 BIOS 中手动切到核显模式，外接屏也将不可用（这是硬件拓扑决定，不是软件限制）。
- 外接屏走向：**独显**，因此它不受「核显模式」以外的模式影响。

## 6. 为什么 `graphics.mode` 不升级

约定 §1.2 规定升级需要「实机调用记录 + 读回值与请求一致」。本任务：

- **没有任何写入**（未定位到写入路径）；
- **没有任何读回值**（无状态接口）；
- 只有「接口不存在」的负向证据。

因此**没有任何可以推动升级的证据**，等级维持 `Unknown`。
升级等级须同时修改 `Capabilities`（任务 01）与 `docs/hardware-evidence.md`；
本任务只**追加证据**（§12），不改动 `Capabilities`。

## 7. 明确未采用的做法（任务书 §9.3）

| 做法 | 为什么不用 |
|---|---|
| 设备管理器禁用/启用独显 | §9.3 明令禁止冒充核显模式；且不会真正切换 MUX |
| NVIDIA 控制面板「应用 GPU 偏好」 | §9.3 明令禁止冒充 MUX 切换；它只影响渲染，不改变显示输出路径 |
| 混淆 MUX 与 Advanced Optimus | 二者机制不同，混用会误导用户（本机是否存在 Advanced Optimus 未确认） |
| 猜测 `Data` 结构 / EC 寄存器 / UEFI 变量名 | §1 原则 5 禁止猜测；猜测可能触发非预期固件行为 |
| 自动重启设备 | §9.1 禁止；本程序不含任何重启代码 |

### v1.1（2026-10-17，会话「奶龙」）：切换通道确立，解除禁用

- **根因澄清**：任务 06 的「确认不支持」不是代码缺陷，而是当时缺少可援引的协议依据；

  UEFI 变量 `MsiDCVarData` byte[1] 目标模式 + EC `0xD1` 触发 + EC `0x2E` bit6 MUX 选择；
  本机只读对照三项（0x2E=0x1B、0xD1=0x00、UEFI byte[1]=0x00）与混合拓扑一致。
- **落地**：`Ms15M3GraphicsModeWriter`（本模块）实现写入路径；`graphics.mode` 升 Verified
  （用户授权 2026-10-17）；`graphics.mux` / `graphics.switch` 寄存器登记入
  `Ms15M3EcRegisterMap`；EC 写白名单新增 0x2E/0xD1（ApplicationHost）。
- **语义修订**：`GraphicsHardwareState.WouldDisconnectExternalDisplay`（Core）按 §12.1 实测修订——
  仅「核显模式」会使依赖独显的外接屏断开；混合模式保留独显输出（本机外接屏即由独显驱动）。
- **仍不支持**：「核显模式」无 MUX 编码，按钮保持禁用并说明原因。
- **生效方式**：写入成功后需重启设备，本程序不自动重启（任务书 §9.1）；
  首次实机写入以应用日志为准，读回不符一律报失败。
