═══ 三、你的职责 ═══

负责 MsiControl.Performance，以及
src/MsiControl.Hardware.Msi/Devices/Ms15M3/Performance*.cs（文件归属见任务书 §15.1）。

1. 调查并验证本机的写入能力
   对每一项确认：是否可写、可写范围、是否被固件锁定、是否需要特权、
   读回是否与请求一致。用 Get_Range 之类的接口查询实际支持范围，

2. 五档可编辑配置
   节能 CPU 10W / GPU 20W；安静 50W / 80W；平衡 60W / 90W；
   高性能与狂暴恢复原生上限。取自 PerformanceProfileCatalog，不要另建表。
   每档独立保存：CPU 持续功耗、CPU 短时功耗、CPU 睿频上限、GPU 功耗上限、
   GPU 兼容节能策略，以及该档的 CPU/GPU 风扇曲线引用。

3. 原生上限必须正确表达
   使用 LimitMode.Native。**严禁用 0、-1 或极大数字表达「无限」**。
   PowerLimit 与 CpuTurboLimit 的构造函数是私有的，只能经 Native 或 Custom(w) 构造，
   不要试图绕过。原生上限的含义是「取消本软件额外限制、恢复设备原生策略」，
   不是绕过硬件保护。

4. CPU 限制的诚实表达
   - 默认严格限制：持续与短时上限尽可能都受设定值约束。
   - 必须解释限制机制的时间窗口可能允许瞬时偏差，
     **不能承诺每次采样都低于设定值**。
   - 不使用 Windows 处理器百分比设置冒充精确瓦数限制。
   - 不使用「禁用睿频」冒充可调的精确睿频上限。
   - 睿频上限优先以频率单位（MHz）表达。
   - 明确报告不可写、被锁定或被固件覆盖的项目。

5. GPU 替代策略
   优先使用本机支持的功耗限制接口。
   目标值不受支持时（例如 20W 可能低于硬件下界）：
   - 用 Get_Range 之类的接口报告**实际支持范围**；
   - **不静默替换目标值**；
   - 如需降级，填入 GpuEcoFallback 并明确标注为替代策略；
   - 明确说明该策略**不保证精确达到目标瓦数**；
   - 不扩展为未授权的 GPU 超频或 VF 曲线编辑。

6. 高性能与狂暴
   均使用原生上限与各自独立的风扇曲线。狂暴**不自动开启强冷**。
   不预设本机支持 APEX / Surge 之类增强模式。
   若实测表明两档没有额外性能能力差异，**明确说明两档主要由散热配置区分**，
   不虚构增强能力。

7. 操作结果必须逐项可查
   每一项都记录：请求值、接口结果、读回值、确认依据、以及
   成功 / 部分成功 / 失败 / 不支持的状态。
   用 ControlResult.From(...) 归并整体状态，不要手工指定。
   **低负载下实际功耗小于目标，不能单独证明限制生效**——
   需要构造有效负载并读回实际限制值来确认。

8. XTU / Afterburner 共存
   检测可识别的冲突来源；显示设置被其他程序覆盖的状态；
   不通过无休止重写争夺控制；不修改或删除其配置；不自动停止或卸载它们。
   具体冲突来源可能需要用户配合确认。

═══ 七、已知编码陷阱（基线中已踩过，直接遵守）═══

- xunit v2 不提供隐式 using，测试文件必须显式写 using Xunit;。
- record 陷阱：可空位置参数传裸 null 会被解析到 record 自动生成的拷贝构造函数
  （参数为不可空引用类型），触发 CS8625。必须用命名参数，如 new(ActiveStage: null)。
- PowerLimit / CpuTurboLimit 构造函数私有，只能用 Native 或 Custom(w)；
  TryCustom 会拦截 0、负数与超过 MaxCustomWatts 的值。
- ControlResult.From 的归并规则是确定性的（全失败→Failed；部分失败→PartiallySucceeded；
  有不支持→PartiallySucceeded；有 PendingRestart→PendingRestart）。不要绕过它自定状态。
- 单位换算只走 MsiControl.Core.Measurement；功耗内部用 decimal，避免浮点累加误差。
