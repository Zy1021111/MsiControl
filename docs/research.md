# MSI-Control 调研与选型记录

本文记录 MSI-Control 的调研背景、候选方案、评估方法与选型依据。
凡结论必须能指回证据；凡未取得证据的判断一律标注「待补充」，不用推测代替实测。

---

## 1. 研究背景与目标

### 1.1 背景

MSI 笔记本在 Windows 下缺少「轻量、本地、直接操作硬件」的控制工具：
官方控制中心偏重且与机型绑定，同类开源工具中最成熟的 G-Helper 面向 ASUS 设计，
不能直接用于 MSI 机型（design.md §1）。MSI-Control 的目标是在首要适配机型
**MSI Vector 16 HX AI A2XWHG / MS-15M3** 上，交付一个**可在实机运行**的本地控制台，
而不是静态界面或模拟演示（任务书 §1）。

### 1.2 研究目标

| 编号 | 目标 | 落点 |
|---|---|---|
| R1 | 摸清同类工具的做法与边界，确定可借鉴与不可复用的部分 | design.md §15 |
| R2 | 逐项验证本机硬件接口的**真实可达性**与证据等级，把「接口存在」与「功能可用」分开 | docs/hardware-evidence.md |
| R3 | 在实测数据基础上完成技术栈与架构选型 | design.md §13、§16 |
| R4 | 把调研结论固化为可判定的工程纪律，防止后续开发按假设行事 | 任务书 v1.2 修订目标 G1–G5（见 §1.3） |

### 1.3 与任务书修订目标（G1–G5）的关系

任务书 v1.2 的修订判据即本调研产生的证据（任务书 §0.3）：

| 编号 | 目标 | 本次调研的对应动作 |
|---|---|---|
| G1 状态同步 | 消除已过时表述 | 证据清单随任务推进追加 §11–§14，旧结论显式标注「维持不变 / 不关闭」 |
| G2 消除歧义 | 统一状态语义、明确技术栈版本 | 能力等级四档落码；技术栈定为 C# + .NET 8（net8.0 / net8.0-windows） |
| G3 补齐可执行性 | 原则落成可判定规则 | 「接口存在 ≠ 功能可用」「读回未确认不称成功」写成执行原则 |
| G4 风险前置 | 已探明约束写在前面 | 「传 null 的 Data 会被 WMI 拒绝」等运行期结论进入各任务提示词 |
| G5 与实测证据挂钩 | 功能项标注候选接口与证据等级 | 每个功能项对应能力键 + 证据章节 + 等级 |

## 2. 调研对象与候选方案

### 2.1 同类工具（design.md §15 分类）

| 角色 | 项目 | 用途 |
|---|---|---|
| 主要参考 | [G-Helper](https://github.com/seerge/g-helper) | 轻量、紧凑、直接操作笔记本厂商接口的工具形态（面向 ASUS） |
| 辅助参考 | [Lenovo Legion Toolkit](https://github.com/LenovoLegionToolkit-Team/LenovoLegionToolkit) | 另一品牌的完整功能组织方式 |
| 辅助参考 | [NBFC](https://github.com/hirschmann/nbfc) | 笔记本风扇控制的通用思路 |
| 辅助参考 | [LibreHardwareMonitor](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor) | 传感器读取的通用库形态 |
| 交互参考 | [M-Control](https://github.com/Sakura-Lhy0409/M-Control-Releases)（闭源） | MSI 机型风扇控制的交互参考 |
| 交互参考 | [FanControl](https://github.com/Rem0o/FanControl.Releases)（闭源） | 风扇曲线编辑交互参考 |

> M-Control 与 FanControl 主程序为**闭源参考**，不作为可直接复用的开源实现（design.md §15 原文）。
> 对 G-Helper 等项目的核对项（UI 与硬件控制边界、风扇与功耗应用流程、配置保存、休眠唤醒、
> 托盘与窗口生命周期、退出后状态、依赖 / 权限 / 资源策略、许可证）见 design.md §16.1。
> 逐项核对结论：待补充（本文只记录已取得证据的部分）。

### 2.2 硬件访问接口候选

| 候选通路 | 预期用途 | 调研结果（详见 §3、§4） |
|---|---|---|
| `MSI_ACPI` WMI 类（`Get_*` / `Set_*`） | 厂商控制面：风扇、功耗、档位、EC | 方法清单与元数据已实机取得；读取部分部分确证，**写入全部未确证** |
| 通用 ACPI 热区 `MSAcpi_ThermalZoneTemperature` | CPU 温度 | 可用（注意口径为热区温度，非 CPU 封装温度） |
| PDH `pdh.dll` 处理器性能计数 | CPU 频率 / 利用率 | 可用，热路径约 0.6 ms / 0.2 ms |
| NVML `nvml.dll`（进程内） | 独显温度 / 频率 / 功耗 / 利用率 / 显存 | 可用；风扇百分比与功耗限制在该卡上 Not Supported |
| `root\WMI:BatteryStatus` | 电池侧功率 | 可用（仅拔电放电时有读数，口径 BatterySide） |
| `Win32_OperatingSystem` | 内存占用 | 可用 |
| 注册表 SMBIOS 快照 | 设备标识 | 可用，本机识别为 Vector 16 HX AI A2XWHG / MS-15M3 |
| `Win32_VideoController`（`Availability`） | 独显是否断电 | 可用，作为 NVML 错误码之外的独立判据 |
| WMI 性能计数类 `Win32_PerfFormattedData_Counters_ProcessorInformation` | CPU 指标 | **否决**：单次访问阻塞约 270 ms，不适合每秒采样 |

### 2.3 技术栈候选

| 候选 | 结论 | 依据 |
|---|---|---|
| C# + .NET 8 + WinForms（单进程） | **采用** | design.md §13「优先验证 C# + WinForms」；与 WMI / PDH / NVML 集成成本低；见 §5.1 |
| WPF | 对照方案，未实测 | design.md §13.2 要求以功能完整性、内存 / CPU 实测、发布体积、曲线编辑体验、主题与 DPI、硬件库集成成本六项对照；**对照实测待补充** |
| Electron / WebView2 承载界面 | **排除** | design.md §13.1 原文「不使用 Electron 或 WebView2 承载界面」：运行时体积与内存负担与「尽量降低内存 / CPU / 安装占用」的产品目标冲突 |
| 多进程 / 额外 Windows 服务 | 排除 | design.md §13.1「优先单一常驻进程」「不预设额外 Windows 服务」 |

## 3. 评估方法与实验过程

1. **证据分级登记**：每条结论在 `docs/hardware-evidence.md` 中按来源编号登记
   （E1 WMI 导出、E2 公开产品文档、E3 只读实机实测等），不把文档说明当实测。
2. **受控只读实测**：所有探测先只读；每次记录耗时、返回类型、失败原因；
   同一结论要求多来源交叉印证（如 `MSI_ACPI` 方法清单要求 E1 与 E2 一致）。
3. **能力等级制度**：每个能力键按证据落级——
   `Verified`（已确证）/ `Detected`（已探测）/ `Unknown`（未知）/ 未适配机型（不存在）。
   只读入口要求 `Verified` 或 `Detected`；**写入入口唯一条件是 `Verified`**
   （任务书 §16.1）。没有对照证据不升格，本次监控侧实测即按此纪律「全部维持不变」
   （hardware-evidence.md §14.6）。
4. **防虚假成功纪律**：读回未确认不称成功；未知 / 失败按语义判定；
   不可用项如实返回 `Unavailable` 并附原因（hardware-evidence.md §14.5 整机功耗口径
   即典型：不用 CPU+GPU 之和顶替）。
5. **噪声排除**：`MSiSCSI_*`、`MSIde*`、`ISR_MSI` 等与本品牌无关的 WMI 项
   已从证据中剔除并单独记录（hardware-evidence.md §6，任务书执行原则 12）。
6. **资源与启动实测**：采样循环 20 次统计单次耗时与 CPU / 内存增量；
   桌面壳启动按日志时间戳分段计时（方法与数值见 `docs/resource-baseline.md`）。
7. **回归测试基座**：全部结论可被自动化测试守护；能力门控发生在调用硬件适配层之前，
   故 737 项测试在无硬件参与下也能验证「未确证不写入」。

## 4. 评估结果摘要（按接口）

| 对象 | 结论 | 证据位置 |
|---|---|---|
| 设备标识 | 注册表 SMBIOS 读取成功：Vector 16 HX AI A2XWHG / MS-15M3，BIOS E15M3IMS.117 | hardware-evidence.md §4 |
| `MSI_ACPI` 接口形态 | 40 个方法的 `WmiMethodId` 实机读出；方法签名模式已确证 | §2.3、§2.6 |
| `MSI_ACPI` `Data` 参数 | 传 `null` 会被 WMI 层拒绝；运行期正确形态已确证（重大推进） | §11.2、§14.1 |
| `Get_EC` | 返回真实内容（EC 固件字符串），但 `ReturnValue` 未暴露，**无法判定固件是否接受调用** | §14.2 |
| `Get_Fan` | 编码未验证，未确证读取路径 → 风扇 RPM 一律 `Unavailable` | §13 |
| CPU 封装功耗 | `Get_Power` 编码未验证，Windows 无 RAPL 包装度量 → `Unavailable` | §11 |
| CPU 温度 / 频率 / 利用率 | ACPI 热区 + PDH 组合可用 | §5、§14.4 |
| GPU 读取 | NVML 进程内可用（温度 / 频率 / 功耗 / 利用率 / 显存 / 降频阈值） | §14.3 |
| 独显休眠判定 | `Win32_VideoController.Availability` 独立于 NVML 错误码，更可靠 | §14.3 |
| 整机功耗 | `power.system` 维持 `Unknown`，按制度不读取 | §14.5 |
| SSD 温度 | SMART / 存储 API 无实例 → `Unavailable` | §14（扩展传感器清单） |
| 显卡模式切换 | 未定位到任何可用写入路径（已确证「不可用」本身） | §12.3 |
| 风扇曲线 / 强冷 / 校准 | 只读侧未确证，写入未开放 | §13 |
| 第三方冲突 | 已知产品进程扫描机制可用（本机样本：检测到 Intel XTU 的 `XtuService`）；策略为只报告不干预 | 任务书 §11 |

> 结论形态说明：本次调研的多个重要结论是**「某条路走不通」的已确证否定**。
> 否定结论同样是证据，直接决定界面显示「不可用 + 原因」而不是留空或造假值。

## 5. 结论与选型依据

### 5.1 技术栈：C# + .NET 8 + WinForms，单一进程

- **依据 1（设计决定）**：design.md §13 优先验证 C# + WinForms，排除 Electron / WebView2
  与多服务方案。
- **依据 2（集成成本）**：所有选定数据通路（WMI 经 `System.Management`、PDH / NVML
  经 P/Invoke）在 .NET 下均为进程内调用，无外部命令进程，符合 design.md §13.4
  「不周期性创建外部命令进程采样」。
- **依据 3（资源目标）**：产品目标即压低内存 / CPU / 体积 / 启动耗时；
  WinForms 桌面壳实测启动到窗口显示约 2.6 s、常驻工作集约 85–90 MiB
  （`docs/resource-baseline.md` §3）。
- **遗留**：WPF 对照实测未执行（待补充，见 §6）。

### 5.2 数据通路选型

- CPU 指标走 **PDH**（否决 WMI 性能计数类的 270 ms 阻塞）；
- 温度走 **ACPI 热区**（公开、稳定，口径如实标注）；
- GPU 走 **NVML 进程内**（避免外部进程与独显唤醒开销）；
- 电池侧功率走 `root\WMI:BatteryStatus` 并以扩展传感器带口径呈现；
- 设备标识走**注册表 SMBIOS 快照**；
- 厂商控制面统一收敛到**共享只读 `WmiMsiAcpiTransport`**（白名单只放行 `Get_*`）。

### 5.3 架构选型：模块化 + 能力门控 + 串行协调器

- **模块化**：9 个生产工程按任务分工（任务书 §15.1），「先确定接口，再逐步接入宿主；
  不等所有模块完成才首次整合」（design.md §13.3）；发布仍是单进程。
- **能力门控**：写入唯一条件是 `Verified`；门控位于协调器内、**先于**调用硬件适配层，
  因此安全语义可被无硬件回归测试守护。
- **串行协调器**：写入统一协调、区分请求状态与实际状态、长操作不阻塞 UI、
  最新用户操作优先（design.md §13.4）；供电变化与启动恢复不得覆盖更新的手动选择
  （任务书 §11）。
- **诚实性保证**：适配层缺失时协调器返回「未接入」，采样缺失时界面显示「不可用」，
  绝不用模拟数据填充（design.md 诚实性约定 / 任务书执行原则 6）。

### 5.4 功能范围裁剪

按 design.md §3 排除电池保护与校准、灯效、屏幕校色、BIOS / EC 刷写、FPS 叠加层、
GPU 超频与 VF 曲线、云账号 / 遥测 / 自动更新。裁剪依据有二：其一，这些方向本次调研
**未取得可靠的写入证据**（如显卡模式切换「未定位到任何可用路径」，§12.3）；
其二，与「不自动刷固件、不关闭安全保护、不修改第三方配置」的执行原则冲突
（任务书 §1 执行原则 9）。范围可以随证据增加而扩展，扩展路径即「能力键升级 +
公告 + 门控放开」，不靠改文案实现。

### 5.5 许可与复用策略

目标为公开开源；复用第三方代码前确认许可证、署名与分发义务；M-Control / FanControl
为闭源参考，不复用其实现；项目自身许可证在完成依赖审查后确定（**待补充**，
design.md §15）。
